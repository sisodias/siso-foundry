Foundry core — shared contracts

What this file is: the three concepts every Foundry domain SHARES, written once here so GitHub, YouTube, and future domains reason about identity, ranking, and value-truth the same way. These are not abstractions invented top-down — each is an already-mature primitive proven in one domain, promoted to core so the other domains adopt it. Companions: core/paths.py (the one DB-path indirection) + core/db.py (the read-only / single-writer connection helpers). Map: FOUNDRY.html. Last updated 2026-06-26.

The two laws every reader obeys (enforced by core/db.py): (1) single-writer-per-DB — exactly one always-on collector (on the mini) writes each domain DB; everyone else opens it read-only via connect_ro(). (2) one path indirection — never hardcode a DB path; resolve through core/paths.py so identical code finds the right file on mini (engine) vs laptop (cockpit). The three contracts below are data/method contracts that sit on top of those two infra laws.

1. The identity model — canonical id + append-only observation

Origin: GitHub (domains/github/catalog.py, tables repo_identity + repo_observation). This is the MATURE identity primitive → core adopts it for every domain (repos, channels/people, papers…).

The problem it solves: the same content unit is seen many times, from many sources, under slightly different URLs/handles. Naive dedup overwrites history and loses provenance. Foundry's answer: two tables, never overwrite a sighting.

TableRoleKey fields
<unit>_identity (e.g. repo_identity)ONE canonical row per real-world unitcanonical_id (PK), stable external id when known (github_node_id), confidence, first_seen/last_seen, normalized_url
<unit>_observation (e.g. repo_observation)APPEND-ONLY log of every sightingobs_id (PK), canonical_id (FK), observed_url, source, source_format, stars, observed_at, UNIQUE(source, normalized_url)

Rules:

  1. Normalize first. Collapse URL/handle variants to one normalized_url (lowercase owner/repo, strip .git, drop www., etc.). The normalized form derives the canonical_id.
  2. Provisional id until a real id arrives. Before a stable external id (GitHub node id) is known, canonical_id = "provisional:" + sha256(normalized_url). When the real id is observed later, the identity can be promoted/merged — observations stay attached.
  3. Confidence GROWS with corroboration. Each independent sighting raises confidence: min(0.95, 0.50 + (n_observations − 1) × 0.05). One source = 0.50; many agreeing sources → 0.95. This is how "is this real / how sure are we" is encoded without a human.
  4. Never delete a raw observation. Dedup is represented by identity rows + provenance, not by overwriting. The append-only log is also mirrored to JSONL (raw/round-NNNN.jsonl) for replay.

For a new domain: create <unit>_identity + <unit>_observation with the same shape, write a normalizer for that domain's URLs/handles, and reuse the confidence rule. YouTube channels and L2 people should adopt this exact pattern (the mini domains/people/people.sqlite person/external_ids tables are the people instance of it).

2. The ranking primitive — 6-dim weighted composite + tiers

Origin: the YouTube research adapter's scripts/scoring/engine.py, class ChannelScorer. This is the mature ranking primitive → core adopts it for ranking people (and any unit) in every domain.

Rank any set of units (channels, creators, repos) by a transparent weighted blend of independent quality dimensions, then bucket into letter tiers. The composite:

overall = Σ (clamp(dimension_score, 0, 100) × weight)      # weights sum to 1.0
tier    = S(90-100) · A(80-89) · B(70-79) · C(60-69) · D(0-59)
missing dimension → conservative default (50)
DimensionWeightMeasures
knowledge0.25knowledge density / educational value
engagement0.20audience engagement quality
consistency0.20regularity + sustained quality
quality0.15production quality
impact0.15long-term value / influence
novelty0.05uniqueness / originality

Why it's the right primitive: dimensions + weights are explicit and tunable (validated to sum to 1.0), defaults are conservative so missing data never inflates, and tiers give a coarse human-readable bucket on top of the fine score. The production variant (engine_v2.py) keeps the identical composite+tier shape but swaps in domain-tuned dimensions (siso_relevance, freshness, tech_recency, actionability, duration_score, consistency) — proving the primitive generalizes: pick 6 dimensions for the new domain, set weights summing to 1.0, reuse the composite + tier logic.

For GitHub L2 (people): rank creators (Karpathy, Steinberg, …) with this engine — define person dimensions (e.g. repo impact, release cadence, adoption of their work, novelty) and reuse calculate_overall_score + get_tier unchanged.

3. The adoption-signal method — ground-truth value corroboration

Origin: GitHub (research/goals/adoption_eco.py + score_and_load.py, table bank_adoption). The "God-source" signal: it corroborates a README-derived value guess against the world's real usage of the thing.

A value rating read off a README is a claim. Adoption is truth: how much is this actually downloaded and depended-on? The method turns external registry usage into a 0–100 score and a promote/confirm/demote verdict.

  1. Resolve the unit to a package via ecosyste.ms (one free API over npmjs.org / pypi.org / crates.io; 5000 req/hr). Guess package name from repo name; fall back to repo→packages lookup. Verify the package's repository_url points back to the source repo — only then resolved=1 (no back-link = weak/unresolved, no false signal).
  2. Pull the signal: downloads (last-month for npm/pypi; total for crates, damped ×0.75 since it inflates), dependent_repos_count, dependents, percentile rankings.
  3. Score 0–100 (log-scaled blend): adoption_score = 0.6·dl_score + 0.4·dep_score, where dl_score = log10(downloads)/9·100 and dep_score = log10(dependents)/6·100. Unresolved → NULL (no signal, README stands).
  4. Verdict vs the README claim: map reuse_value 65→88 to an expected band 35→75. adoption ≥ expected+15 → promote (under-sold); adoption ≤ expected−20 AND the package is a canonical name-match (not a fork/example) → demote (README over-sold); else confirm. The canonical-match guard stops fork/example sub-packages from unfairly demoting.

The point: adoption is a signal a frontier model can't get from its weights — it's live, external, ground-truth usage. It's the data-layer moat (per the North Star). For a new domain: find the domain's equivalent "real usage" signal (views/subscribers for YouTube, citations for papers) and apply the same resolve → log-score → verdict-vs-claim shape.

How the contracts compose (one sentence)

Each domain resolves units to a canonical identity (contract 1, append-only + confidence), ranks the people/units behind them with the 6-dim composite (contract 2), and corroborates the value claim against real-world adoption (contract 3) — three shared methods, one per "what is it / who's good / is it really valuable", reused across every domain.
