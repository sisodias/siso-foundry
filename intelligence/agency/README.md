# Agency intelligence

This package is the durable, publication-safe front door for using Foundry to build **SISO Agency OS**: an agent-native business operating system intended to combine evidence-reviewed source products, SISO-owned control-plane capabilities, and outcome-backed integrations.

Foundry answers three questions:

1. What useful source already exists?
2. What does the evidence say about adopting, adapting, integrating, or rejecting it?
3. Which owning SISO Work should prove and release the resulting capability?

The Great Library of SISO records the stable identity, release, selection, and promotion lineage. It does not absorb this repository or the operational corpus. Foundry remains an independent Research Work and owns source discovery, reuse intelligence, and verification evidence.

## The operating loop

```text
Agency need or industry problem
  -> Foundry source discovery and direct review
  -> adoption mode: use whole / API / sidecar / extract / reference / build
  -> behavioral and composition proof
  -> Library Source Inventory and owner assignment
  -> owning Work release
  -> Agency OS capability adapter, policy, approval, and audit surface
  -> production outcome evidence back into Foundry
```

This makes the Library the findable map, Foundry the source-intelligence engine, and Agency OS the product that applies the evidence. A repository with many stars is a candidate, not a product decision.

See the deterministic [`coverage inventory`](COVERAGE.md) and [`machine-readable coverage rows`](coverage-inventory.json) for repository-level deduplication, canonical 12-pillar mapping, evidence splits, and reusable-analysis counts.

## Recovered intelligence

The metadata snapshot at [`snapshot.json`](snapshot.json) records the observed shape of the external Foundry data plane without publishing the database or generated artifacts. It includes exact logical-source receipts, component timestamps, file sizes, and SHA-256 digests so later agents can reproduce the same population. As rechecked on 2026-08-02, the corpus includes:

- 1,358,200 repository identity cards across 264 categories;
- 23,778 bank repositories and 32,137 ranked liftable candidates;
- 2,722 adoption decisions: 429 promote, 1,186 confirm, 228 demote, and 879 unresolved;
- 70 total contract cards, with a separately identified 20-card verified harness subset: 13 at trust rung 3, 14 self-smoked, and 6 import-smoked;
- a 104-node, 124-edge capability graph;
- 707 proof selections across 119 groups; and
- 62 agent patterns, 26 prompt-corpus records, and 259 repository source signals.

These numbers are timestamped observations from older source components, not a claim that the corpus is downloadable or current forever. A content hash identifies what was queried, but the external assets still require rights and privacy review, schema receipts, generator receipts, and durable-copy receipts before any dataset release.

## Agency application map

The application map below is the portfolio overview. The decision-grade, scored source of truth is the [`SISO Agency OS value matrix`](VALUE-MATRIX.md), backed by [`value-matrix.json`](value-matrix.json). Its unit is `repository × SISO use case × adoption route`, because a repository does not have one universal value or one universal reuse verdict.

| Capability cluster | Candidate products | Default integration posture |
|---|---|---|
| Structured work and CRM | Teable | Source-owned module behind SISO identity, capability, policy, and audit adapters |
| Documents and knowledge | AFFiNE / SISO Docs, Open Notebook | Source-owned module or service; keep storage ownership explicit and expose agent-safe actions |
| Delivery and projects | Plane | Adopt whole or integrate by API before extracting narrow reusable capabilities |
| Contracts and signing | Documenso | Sidecar or API integration; legal records remain owned by the signing system |
| Support and communications | Chatwoot | Source-owned service with channel, consent, and approval boundaries |
| Scheduling | Cal.com | API or embedded module with SISO identity and event lineage |
| Automation | Activepieces | Controlled execution plane; Agency OS owns authority and audit, not every connector implementation |
| Marketing | Listmonk, Postiz, Formbricks | Separate delivery systems behind shared contacts, consent, metering, and campaign policies |
| Analytics | Metabase, PostHog, Superset | Read-oriented services over governed data products; no direct cross-module writes |
| Search and AI memory | Meilisearch, Qdrant, RAGFlow | Shared retrieval infrastructure with tenant, provenance, and retention controls |
| Hosting and data movement | Coolify, Airbyte, dlt, Meltano | Infrastructure modules operated through explicit deployment and data-contract capabilities |
| Agent builders | Langflow, Coze, Flowgram | Candidate orchestration surfaces; agents still act through SISO capability and approval contracts |

Every entry is an **operator-nominated idea**, not a Foundry-backed selection, until a current source, license, maintenance, security, tenancy, and operability review is recorded. Names here are a starting portfolio, not endorsements or accepted Library Works.

## The SISO-owned leverage layer

Source products provide deep domain functionality. SISO Agency OS should own the layer that makes them work as one agent-native business system:

- identity, tenancy, and authority;
- capability discovery and action contracts;
- approval policy and human escalation;
- append-only business audit and provenance;
- usage metering, pricing, and entitlements;
- reliable webhook and event delivery;
- cross-module data contracts and read models; and
- outcome measurement that feeds adoption evidence back to Foundry.

The current corpus did not reveal clean, universally droppable source for six recurring product-glue problems: usage metering, pricing and entitlements, multi-tenancy, append-only business audit, reliable webhook delivery, and an OAuth authority server. Those gaps are high-value SISO control-plane IP unless later evidence changes the verdict.

## What the evidence does not prove

The composition experiments do not support a claim that arbitrary repositories snap together into a working application. The strongest verified result is narrower: structured cards and verification contracts can improve selection, steering, and the detection of invalid hand-rolled behavior. That is useful leverage, but it still requires an owner, integration code, and product proof.
