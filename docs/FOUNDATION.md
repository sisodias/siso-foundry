# Foundry foundation and operating model

Status: source-first operating clarification, 2026-09-07. This document does not
transfer ownership, activate a service, admit a product or publish a dataset.
Implementation findings and exact revisions are in the
[source audit](SOURCE-AUDIT-2026-09-07.md).

## 1. Start with the decision, not the warehouse

Foundry's useful output is a defensible answer to a named source-selection need.
A million discovered repositories are not a million reusable capabilities.
A high score is a prioritisation hypothesis, not evidence of value, correct
licensing, tenant isolation or a working integration.

The existing [application mission](AGENCY_OS_APPLICATION_MISSION.md) establishes
this demand-first loop and its evaluation gates. This foundation does not replace
its adoption vocabulary, business pillars, product owner or research records.

For every investigation, state: the consumer, the decision it must make, what is
already known, what uncertainty matters, and what evidence would change the
choice. A run without those fields is not ready for broad acquisition.

## 2. Preserve responsibility at the interfaces

```text
Question or product owner: need + decision criteria
                   |
                   v
Foundry: discover -> identify -> qualify -> supply evidence references
          ^                     |
          |                     v
Existing supply           Evidence Engines: explicit source-grounded transforms
and targeted gaps               |
                                v
                  Question/product owner: reason, decide, test
                                |
                   safe accepted research/release metadata
                                v
                    Great Library: identity + lineage + selection
```

SISO Knowledge and the Knowledge Graph remain independently owned corpus,
provenance and retrieval systems. People Graph remains an independently owned
identity/relationship system. Foundry may supply references or request bounded
reads; it must not redefine their schemas, migrate their databases or create a
replacement graph merely because related code exists in this checkout.

Evidence Engines' public README describes explicit JSON inputs and no discovery
or network requests in its first release. Foundry should supply well-qualified
inputs to that boundary, not claim an already-operational automatic connection.
Product execution and client data remain with their product/client owners.
The Great Library registers and selects public research; it is not the raw
warehouse or a compute runtime. See the pinned public sources in the audit.

## 3. Keep three planes distinct

**Source plane:** Git code, contracts, schemas, reviewed metadata, small fixtures
and provenance. Source availability can be tested without the real warehouse.

**Data plane:** observations, database snapshots, transcripts, intermediate
artifacts and private evidence. Access is asset-specific. A manifest is a locator
and a dated claim, not the payload or an access grant.

**Execution plane:** an authorised machine or service, configured inputs,
credentials, a responsible operator, budget, output locations and stop conditions.
Neither repository permission nor a dataset read proves execution readiness.

Always report GitHub, each other connector, laptop, Mini and VPS separately.
Never infer current machine health from a historical architecture diagram.

## 4. Evidence must retain its scope

A useful handoff preserves the existing owner, source locator, observation date,
privacy level and exact revision. Where available, include a content hash and
bounded selection method. Hash equality establishes byte identity, not authorship,
truth, representativeness, source rights or approval.

Keep these statements different:

| Statement | What it establishes | What it does not establish |
|---|---|---|
| Repository metadata read | A locator and metadata were observed | Relevant code was inspected |
| Source paths read at a commit | Particular code/docs were inspected | Claimed behavior actually ran |
| Synthetic fixture passed | The tested code behaved on that fixture | Production data or integration works |
| Explicit local dataset matched | A bounded input matched the checked contract | Whole-corpus coverage or safe redistribution |
| Owning product test passed | Behavior in that named host was measured | Universal portability or business outcomes |
| Outcome observed | A specified result occurred under stated conditions | Causation, repeatability or cross-client value by default |

Do not replace existing evidence-state enums with this explanatory table. Keep
claims in their existing records and make their scope explicit. A new, stronger
claim requires new evidence; it must not be generated by changing a label.

## 5. Prefer existing supply; acquire only for material gaps

Use the existing identity corpus when available and the separately maintained
Repo Bank for bounded recall. Shortlist comparable candidates for the same
primitive, then inspect exact upstream revisions. Do not load entire banks into
model context, flatten upstream repositories, or treat their licenses as inherited
from Foundry.

Targeted acquisition must record the query/version, selected sources, exclusion
rules, date window, quota or budget and stopping condition. Preserve raw
observations append-only; derived views can be rebuilt. Source disagreement,
missing evidence and inaccessible material remain visible.

A campaign definition is not a schedule. A source shortlist is not product
admission. A named owner is not a live-runtime observation.

## 6. Storage and readers

Keep identity independent of the storage path, and use the existing data-root
contract instead of searching home-directory ancestors. Preserve one authorised
local SQLite writer with read-only consumers. The connection helper does not
enforce a fleet-wide writer lease and does not enable WAL; those claims require
separate operational evidence.

Read-only SQLite filenames are encoded as file URIs before adding `mode=ro`.
This prevents filename characters from becoming URI syntax and prevents absent
databases from being created by the reader. The implementation has synthetic
regressions; it does not validate every historic direct SQLite caller.

Configuration reconciliation remains a bounded follow-up: the core helper,
GitHub pipeline and bank scripts currently differ in their path/override logic.
Before unifying them, enumerate consumers, preserve explicit override precedence,
test unset/relative/tilde paths, and prove no unintended database is selected.
Do not move any dataset as part of that code change.

## 7. Verification is not one green badge

`npm run test:source` validates public source and historical record invariants,
runs synthetic tests and the existing dry-run check, and reports that external
data and execution were not checked. CI runs that source-only contract.

`npm test` also requires an explicitly selected atlas consistency check. A missing
atlas is **blocked**, a malformed or mismatched atlas **fails**, and an exact ID
match returns a content-hash receipt. Neither command proves every historical
private check, a complete data-plane release or an operational research engine.

The publication scanner operates on Git-tracked and nonignored candidate files,
not ignored datasets. It reads symlink text rather than following targets and
reports rule IDs rather than secret values. It remains a heuristic: independent
privacy, rights and exact-file review is required before public release.

## 8. Changes, integration and rollback

A scoped branch changes only its owned source paths. Preserve other branches,
unpublished work, existing owner handoffs and immutable research releases.
Record base/head commits, changed files, actual checks and unresolved blockers.
Do not treat a pull request as acceptance by a receiving owner.

A code merge does not update a Great Library Release, Snapshot, deployed site,
external database or running collector. Those transitions retain their own owner
and evidence gates. Roll back an accepted code change with a reviewed revert;
never erase source observations or rewrite another owner's history.

## Next useful research run

Follow the [research-run playbook](RESEARCH-RUN.md): one named need, existing supply
first, a few comparable alternatives, counter-evidence, a receiving owner and a
measurable decision. Expand only when the bounded pilot demonstrates value.
