# A substantial Foundry research/reasoning run

Status: proposed run design, not a scheduled job or execution authorisation.
Use the existing project/question record and owner handoff; do not create a
parallel task queue, question registry or new fleet owner.

## The decision

> Which existing capabilities should the receiving SISO project adopt, connect
to, learn from or reject for a named workflow, and what evidence justifies that
choice over the alternatives?

Foundry owns discovery and evidence supply. The receiving question/product owner
owns the reasoning decision and any authorised implementation. Knowledge Graph,
People Graph and Evidence Engines keep their existing interfaces and ownership.
The [application mission](AGENCY_OS_APPLICATION_MISSION.md) defines adoption routes
and evaluation gates; this playbook tells a run how to apply them.

## Gate 0: a bounded brief and actual access

Before spending on broad research, record the consumer, actual workflow, incumbent,
decision criteria, constraints, acceptable evidence sources, privacy class,
time/cost/request ceilings and stop rule. Budget values must be supplied, not
invented from a plan or inferred subscription capacity.

Record code access, dataset access and runtime access separately. Confirm one
bounded existing input through its native read-only interface. If the intended
input is unavailable, report the gap; do not substitute a fixture or silently
expand into web-wide collection.

## Gate 1: recall from what already exists

Use the existing Foundry/Repo Bank inventory before new collection. Preserve
query terms, repository identities, versions, dates and exclusion reasons.
Shortlist two or three alternatives for the **same primitive**, plus the incumbent
or a do-nothing option. Stars and discovery scores can prioritise inspection but
cannot establish business value or rights.

New external reads should target a material uncertainty, not create a second
warehouse. No bulk downloads, automatic capture schedules or raw private evidence
in public output follow from this brief.

## Gate 2: direct, adversarial qualification

For each shortlisted option, inspect exact source paths and the relevant license
boundary. Separate documented behavior, inspected implementation, tested behavior
and measured outcomes. Preserve incomplete, contradictory and inaccessible sources.

The expensive reasoning should examine integration and removal cost, maintenance,
identity/permission propagation, data ownership, alternative adoption routes,
false-positive value claims and reasons to prefer the incumbent. Ask a reviewer
what would make the leading recommendation wrong.

License conclusions must be scoped to the actual files, edition, version and
adoption route. Repository visibility or a root badge is not general permission.
No recommendation grants external action, customer access or product admission.

## Gate 3: a decision packet, not a giant report

A proposed bounded first tranche is at most ten qualified capability packets and
three experiment proposals. This is a scope suggestion, not an existing output or
permission to create ten agents.

Each packet should retain: named need/consumer; owner and privacy class; exact
source/ref/date; evidence and counter-evidence; alternatives and rejection reasons;
recommended adoption route; unmeasured costs; explicit missing evidence; and the
next experiment with its acceptance criterion and falsifier.

Link to the existing topic, industry or question record. Store private sources
with their current owner; expose only reviewed public-safe metadata through the
existing Library release process. A branch and a research hypothesis are not a
selected, pinned or deployed capability.

## Gate 4: test whether Foundry itself helped

Compare a Foundry-assisted approach with ordinary direct search on the same
predeclared needs and comparable resource budgets. Use held-out needs where
possible, preserve the selection method, and have the receiving owner review
outputs against the same rubric without being told the method when practical.

Measure time to a defensible decision, important risks caught, source traceability,
recommendations rejected after review, receiving-owner usefulness and research
that can be reused on the next need. Count operator review and correction time.
Do not call a hand-selected demonstration causal proof of improvement.

Token volume, report length, repository count and theoretical code-replacement
valuation are not substitutes for these outcomes.

## Pilot selection

Use an actual authorised need first. The existing
[law-firm record](../intelligence/agency/industries/law_firms.json) can serve as a
research-only worked case for supervised intake, approved-template assembly or
source-linked review. Its jurisdiction, missing client baseline, human authority,
rights limits and unmeasured value remain intact. It is not a statement about any
current client or proof of demand.

## Stop and handoff

Stop when the predeclared decision is supported, the material evidence cannot be
obtained within the bounds, or the budget/authority boundary is reached. Report
what changed the recommendation and what remains unknown. Continue acquisition
only for a specific unanswered decision, not because more sources are available.

A proposed run becomes executable only after the appropriate existing owner has
verified inputs, environment, resource limits, destinations and permitted actions.
This source overhaul does not perform that activation.
